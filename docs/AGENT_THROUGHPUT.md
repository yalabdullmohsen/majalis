# بروتوكول تسريع الوكيل (AGENT THROUGHPUT)

يُطبَّق في **كل** مهمة. القياس: `docs/CI_THROUGHPUT.md`. الفهرس: `docs/REPO_INDEX.md`.
سلامة البوابات: `.cursor/rules/majlisilm-ci-safe.mdc` و`pnpm run verify:ci`.

## المسار الإلزامي

```
Targeted Read → Plan → Patch → Focused Test → Full Verify
```

لا تتخطَّ مرحلة. لا تُعِد مرحلة بلا دليل جديد.

### 1) Targeted Read
- ابدأ من `docs/REPO_INDEX.md`.
- حدّد ≤ الملفات المرشحة مباشرة للمهمة.
- اقرأ الملف **كاملًا** قبل تعديله؛ ممنوع patch من مقتطف ناقص.
- لا تُعِد استكشاف ملف قُرئ ما لم يتغير أو يظهر دليل جديد.
- ممنوع بحث عام في المستودع إذا كان المسار معروفًا من الفهرس.
- ممنوع إعادة `rg` لنفس المصطلح بصيغ متكررة بلا نتيجة جديدة.

### 2) Plan
قبل أول تعديل اطبع خطة قصيرة فقط:
- السبب/الفرضية
- الملفات المقصودة
- الفحص المستهدف
- معيار التوقف  
لا تحليل مطوّل ولا سجل تفكير.

### 3) Patch
- أصغر patch مكتمل ضمن النطاق المخطط.
- ممنوع توسيع النطاق بلا دليل جديد موثَّق في الرد.
- ممنوع patch تقريبي لا يطابق محتوى الملف.
- إن فشل patch لاختلاف المحتوى: اقرأ المقطع الدقيق مرة → أعد المحاولة **مرة واحدة فقط**.
- بعد فشل المحاولة الثانية: **توقّف** وبلّغ عن التعارض (لا دوران).
- ممنوع إعادة كتابة ملف كامل لتغيير محدود.
- ممنوع refactor / تنسيق / إعادة تسمية جانبية خارج الهدف.

### 4) حماية بوابات الجودة
- CI والاختبارات = عقود ثابتة.
- أصلح كود المنتج ليمر من البوابة — **لا** تعدّل gate/threshold/baseline/snapshot لتلائم تنفيذًا فاشلًا.
- تعديل بوابة مسموح فقط إذا:
  1. دليل قابل لإعادة الإنتاج أن البوابة لا تطابق عقد المشروع الفعلي، و
  2. معيار الجودة مساوٍ أو أشد، و
  3. اختبار يثبت السلوك القديم الخاطئ والجديد الصحيح، و
  4. يُذكر تعديل البوابة صراحة في مخرجات المهمة.
- ممنوع `continue-on-error` / `|| true` / skip / رفع حدود لإخفاء فشل.

### 5) Focused Test أولًا
- بعد Patch: أصغر اختبار مرتبط بالملف/الميزة.
- عند الفشل: أصلح أول خطأ أصلي فقط.
- ممنوع `verify:ci` بعد كل تعديل صغير.
- Lighthouse / visual / native فقط عند Path-lane أو نطاق المهمة.
- lint/typecheck على الحزمة المتأثرة قبل الشامل.

### 6) Full Verify مرة واحدة
بعد نجاح المستهدف:
1. فحوص الحزمة المتأثرة
2. `pnpm run verify:ci` **مرة واحدة**
- أعد `verify:ci` فقط إذا تغيّرت ملفات بعد فشل سابق.
- ممنوع تكرار التشغيل بلا تغيير.

### 7) فرز فشل CI
- Log لأول job أصلي فاشل.
- صنّف الباقي: أصلي vs تابع.
- لا تعالج aggregator / Path-lane قبل السبب الأصلي.
- Re-run فقط عند دليل عطل بنية تحتية مؤقت.
- أصلح على نفس الفرع ونفس الـPR.

### 8) حدود النطاق
- هدف واحد مترابط · PR واحد لكل مهمة.
- لا تجمع تصميمًا + إشعارات + صوت + migrations + CI في تنفيذ واحد.
- طبقات متعددة مسموحة فقط إن لزمَت نفس معيار القبول.
- مطلب مستقل → follow-up؛ لا تنفّذه تلقائيًا.

### 9) شروط التوقف
أوقف وقدّم تقريرًا مختصرًا إذا:
- تعارض تعليمات المشروع
- قرار مالك مطلوب
- schema / secrets / App Store identity غير مصرّح
- اتسع النطاق لميزة مستقلة
- فشل patch مرتين لاختلاف المحتوى
- الحل يتطلب تخفيف بوابة جودة

### 10) اقتصاد التوكن والبحث
- لا تُعِد تلخيص ملفات السياق كل خطوة.
- لا تطبع ملفات كاملة في الرد.
- لا تكرر الخطة بعد كل تعديل.
- أسماء ملفات + أسطر + نتائج مختصرة.
- اجمع القراءات/الاختبارات المستقلة بأمان عند الإمكان.

### 11) مخرجات المهمة المطلوبة
1. Root cause  
2. Changed files  
3. Focused tests  
4. Full verification  
5. Remaining risks  
6. `git diff --stat`  
بدون سرد كل عمليات البحث أو الرسائل المرحلية.

## دفع ودمج (بعد Full Verify)
1. من جذر git: `pnpm run verify:ci` ناجح قبل commit/push.
2. ادفع → PR Ready واحد → auto-merge squash.
3. راقب الحرجة فقط: `gh pr checks --watch --fail-fast` (Verify build + repo-gates + build + static-checks).
4. عند فشل CI: أصلح محليًا → Focused Test → `verify:ci` مرة → ادفع — **لا تعطّل الفحص**.

## قواعد تشغيلية مختصرة
- دفعة متجانسة ضمن ≤٤٠ ملفًا و≤٤٠٠ سطر حذف عند المهام الكبيرة؛ PR بهدف واحد.
- خيط بلا إغلاق خلال محاولتين أو ١٥د → `docs/DECISIONS_PENDING.md` واقفز.
- قرار بشري (PWA/تراخيص/CSP) لا يوقف الطابور — سجّل واقفز.
